## Description

FlexDesk builds its tooltip at `opacity: 0` and adds a `visible` class on hover to fade it in. No stylesheet says
what `.visible` does, so every tooltip on a `twm-has-tooltip` element is positioned and invisible. Found in Tables
on 2026-10-07; still true in 0.7.0 (`origin/main` @ `410e84d`: no `.twm-latex-tooltip.visible` rule in `css/`).

Tables carries a stopgap in its own `web/css/tables.css`, with a comment to delete it once FlexDesk ships the rule:

```css
.twm-latex-tooltip.visible { opacity: 1; }
```

## Steps to reproduce

1. Give any element `class="twm-has-tooltip"` and a `data-tooltip`, with FlexDesk's tooltip listeners loaded.
2. Hover it.
3. The tooltip element is created and positioned, but stays at opacity 0.

## Expected

The tooltip fades in. The fix is one rule in `css/base.css` and the mirrored `flexdesk.css`, then a release.

The fix: `.twm-latex-tooltip.visible { opacity: 1; }` now sits right after the `.twm-latex-tooltip` rule in both `css/base.css` and `css/flexdesk.css`. The new regression suite is `tests/tooltip_visible.test.mjs`. It hovers a `twm-has-tooltip` element, then checks that the tooltip is built with its text and marked `visible`, and that it computes to opacity 1 while shown and 0 after the mouse leaves. It also checks that both stylesheets have the rule and that it outranks the base rule. The suite passes with the fix. Against the origin/main CSS it fails with 3 assertions and exit 1, so it does catch the bug.

The suite takes about 24 s on /mnt/c, almost all of it file I/O importing widgets.js. It injects only the tooltip rules into the page, because with the whole flexdesk.css, jsdom's getComputedStyle takes minutes.

No public API or exports changed, so the entry files and README are untouched.
