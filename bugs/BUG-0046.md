## Description

`_chordOfEvent` in `src/tiling/keymap.js` reads `e.key` and matches `/^[1-9]$/` to build `Alt+Shift+N`. With Shift held, the browser reports the shifted character: on a US layout, Alt+Shift+2 gives `e.key === '@'`, and on a German layout `'"'`. So the chord is never recognised, and "Move the focused tile to desktop N" only works from the palette or menu. Alt+1..9, which has no Shift, works. `e.code` (`Digit2`) is layout-independent for the digit row.

Found by EcoAgent's shell cutover (EcoAgent STORY-0028, `../EcoAgent/backlog/STORY-0028.md`). EcoAgent's old keymap had the same `e.key` test, so it is not a regression there.

## Steps to reproduce

1. With a shell that has two desktops, focus a tile on desktop 1.
2. Press Alt+Shift+2 on a US keyboard.

## Expected

The focused tile moves to desktop 2, as the keyboard-shortcuts help says.

## Actual

Nothing happens. A synthetic event with `key: '2'`, `altKey`, `shiftKey` does move it, which hides the defect in tests.

## Comments

### 2026-10-26T10:58Z · norman_agent (status: investigation -> testing)

Fixed on main in aed1ffa (dist rebuilt in 31de892). Not released: package.json is still 0.17.13.

Cause as filed: `_chordOfEvent` matched `e.key`, which Shift turns into a symbol. The digit row is now named by `e.code` (`Digit1`..`Digit9`), so a real Alt+Shift+2 moves the tile on US (`@`), German (`"`) and every other layout, and unshifted Alt+1..9 now works on AZERTY. `e.key` is still read for events with no `Digit` code (synthetic events, the numpad), for AltGr (so `{ [ ] @` still type), and for Option on a Mac while focus is in a text field (so the characters Option types still type there).

A review round found a second defect that this fix would have exposed to everyone: `wm.moveFocusedToDesktop(n)` was unguarded. With n equal to the desktop you are on (Shift held by slip while switching with Alt+N), the tile's tabs were appended to its own tree and the focused tile then closed, so the tile was destroyed; with a panel focused, the panel replaced another desktop's home ground. AZERTY already had both through the old path. The method now refuses the desktop you are on and any panel, matching what the tile menu already offers, so the keyboard and the menu cannot disagree (a test pins that).

Tests: `tests/keymap_digit_row.test.mjs` (real key/code pairs for US, German, AZERTY, Mac Option, AltGr; the 55 assertions that fail on the old keymap) and `tests/move_to_desktop.test.mjs` (real `createShell`; 25 assertions fail without the wm guard). Docs: `docs/components/keymap.md`, new section headed "(0.17.14)" (provisional; retag if the release number differs). Full suite: 210 suites, none skipped.

Not verified: no real keyboard, no real Mac. Everything above ran as synthetic events with the key/code pairs those keyboards produce. Please try Alt+Shift+2 once on a real keyboard.

Seen and left alone: Alt+Shift+9 with two desktops still creates desktops 3 to 9 and parks the tile on 9 (shared with Alt+9); Option+Left/Right in a text field on a Mac is swallowed by the Alt+Arrow chords (predates this); the "text field" test only matches `contenteditable="true"`.
